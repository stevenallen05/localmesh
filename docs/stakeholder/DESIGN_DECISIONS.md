# Design decisions

Current state of every design choice — one row each. Implementation specifics (crates, code layout, label syntax) live in [`docs/engineering/`](../engineering/) and the spec at [`docs/superpowers/specs/`](../superpowers/specs/).

Companion: [`ENGINEERING_RULES.md`](./ENGINEERING_RULES.md), [`PROJECT_SCOPE.md`](./PROJECT_SCOPE.md), [`PRODUCTION_DISCUSSIONS.md`](./PRODUCTION_DISCUSSIONS.md).

This repo is a reference implementation of the **microservice-template + service-catalogue pattern** an org would adopt at the CI/CD (Continuous Integration / Continuous Delivery) layer. The Rust + Next.js parts are one team's microservice; observability is a catalogue module the team includes.

## Settled

**Prod-considerations** is row-specific only. The full production assumption set is in [`PROJECT_SCOPE.md`](./PROJECT_SCOPE.md).

| Area | Dev choice | Rationale | Prod-considerations |
|---|---|---|---|
| Vision | One team's microservice + a stub catalogue module. | Demonstrates the org-scale pattern: platform owns catalogue, product owns compose. | Catalogue becomes a real platform product. |
| Orchestration | Compose is source of truth; pre-commit hook generates the Helm chart. | Compose is the practical ceiling for self-service teams; chart is build output. | Chart generation runs in CI; published to an internal registry. |
| Module composition | Compose `include:` pulls catalogue modules — required: `observability/`, `security/`, `logging/`; optional: `database/`. | Required and optional modules added by reference, not copy-paste. | Include path swaps to a platform-published location. |
| Observability module | Off-the-shelf collector + exporters + TSDB (Time-Series Database) + dashboards. | All battle-tested; team adds no value building these. | TSDB swaps to a managed/clustered equivalent at scale. Host-facing scrapers (cadvisor, node-exporter, filelog) are dev-fidelity only; in prod ops owns the equivalent collectors and the team's catalog excludes them via the prod overlay. |
| OTel semconv as the omakase contract | Apps follow OpenTelemetry semantic conventions end-to-end: standard env vars (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`, `OTEL_SEMCONV_STABILITY_OPT_IN=http` for Node); standard metric names (`http.server.request.duration`, `rpc.server.duration`); standard resource attrs promoted to series labels (`service_name`, `service_namespace`, `service_instance_id`, `deployment_environment_name`). Single bootstrap per language: Rust extends `server/src/telemetry.rs` with a `MeterProvider` + `RpcMetricsLayer` tower middleware; Node extends `www/instrumentation.ts` with `HttpInstrumentation` + a `PeriodicExportingMetricReader` via `@vercel/otel`. Collector translates OTel→Prometheus on VM's behalf (`prometheusremotewrite` exporter with `resource_to_telemetry_conversion`); VM has an OTLP receiver but lacks `keep_identifying_resource_attributes`, which the imported dashboard's header stat panels need — the collector path supplies it. Long form: [`docs/superpowers/specs/2026-05-16-otel-semconv-pipeline-design.md`](../superpowers/specs/2026-05-16-otel-semconv-pipeline-design.md). | One env-var convention + one bootstrap file per language gives any new service the canonical OTel dashboard for free. Backend swaps (Mimir / Grafana Cloud / Prometheus 3.x with OTLP receiver) need only the resource-attr promotion knob flipped — apps and dashboards portable. | Add OTLP semconv metrics for outbound HTTP / DB / RPC clients (currently only the Node SDK auto-emits these); add `service.version` from build metadata. |
| Dashboards | Two provisioned dashboards. **`apm`** — imported community dashboard "[Lightweight APM for OpenTelemetry](https://grafana.com/grafana/dashboards/22784)" (Grafana ID 22784, [source](https://github.com/cyrille-leclerc/opentelemetry-service-dashboard)). Application-services lens: RED + inbound HTTP/RPC operations tables + outbound clients + logs + traces. Patched at import: datasource defaults bound to our UIDs, template-variable queries source from `label_values(LABEL)` directly (VM doesn't have `keep_identifying_resource_attributes`), stat-panel filters use `job=~"$service_namespace/$service_name"`. **`cluster-health`** — host/container resources (cadvisor + node-exporter) plus a module-roster panel folded in from the prior `infra-modules` dashboard. Removed: `service-glance`, `service-logs`, `infra-modules` (subsumed). | Importing a community OTel dashboard validates the omakase contract — if it works against this stack, it works against any OTel-conforming stack. Less code, more standardisation. The dashboard's setup notes document exactly what the rest of the OTel ecosystem assumes. | Future per-team dashboards forked from `apm` as the starter; `cluster-health` stays as the infra lens. |
| Module attribution | Every application signal carries the OTel-canonical identity tuple — `service.name`, `service.namespace`, `service.instance.id`, `deployment.environment.name` — plus the two project-specific attrs `module_name` and `owned_by`. All six travel through one channel: `OTEL_SERVICE_NAME` + `OTEL_RESOURCE_ATTRIBUTES` per service in compose. The Rust SDK reads both; `@vercel/otel` (www) does the same; pg_tracing's hardcoded `service.name=PostgreSQL_Server` gets rewritten by the collector's `transform/database`. Resource attrs become labels on every series (collector's `resource_to_telemetry_conversion`) and indexed Loki labels (config in `service_catalog/logging/`). Cadvisor's `metrics.service_name` docker label still becomes a `service` (lowercase) metric label — kept as a *container-resource* lens distinct from the application-identity tuple; the two coexist intentionally. | One identity tuple makes the roster, RED, and owner-attribution queryable across all three signals. The OTel-canonical attrs are what the imported APM dashboard (and every off-the-shelf OTel dashboard) reads. | `owned_by` resolves from the org's team registry rather than hardcoded compose values; `service.namespace` becomes the team/tenant axis. |
| Database module (optional) | Postgres 16 + Datadog's `pg_tracing` extension, custom-built image, OTLP/HTTP push to the collector. Hard-coded sampling at 1.0; `service.name` rewritten `PostgreSQL_Server` → `postgres` at the collector. Server holds a `sqlx` `PgPool` plumbed via `DATABASE_URL`; `sqlx::migrate!()` applies embedded SQL migrations at server startup. Demo `Greeter.PrintPostgresStats` RPC writes one `noise_events` row per click and reads the five headline `pg_stat_database` metrics; each SQL statement carries a `/*traceparent='...'*/` comment so pg_tracing stitches the resulting parse/plan/exec spans under the gRPC server span. Real product use-cases (registry / audit log / events) deferred — they'll define their own schemas alongside `noise_events`. Rollbacks deliberately out of scope: "rollback" means different things across prod targets (managed-DB point-in-time-restore vs. compensating migrations vs. blue/green schema flips); `sqlx::migrate!()` doesn't preclude any of them. | Single image, zero polling glue — pg_tracing emits parse/plan/exec spans as children of any traceparent embedded as a SQL comment, so the trace `user → www → server → postgres` works end-to-end without per-team integration code. | Managed offering (RDS / CloudSQL) with pg_tracing enabled via parameter group; sampling tuned to ~1-5%. Migration-rollback strategy chosen alongside the prod DB target. |
| Server | Rust gRPC. Greeter.SayHello (trace-stitching reference) + Catalog (List/Get for datasources + metrics; full CRUD for dashboards, single-panel single-query model). Traces (application metrics pending re-design); reqwest→Grafana hop is not auto-instrumented, so the Grafana HTTP leg shows as opaque inside the server span. | Preserves the original template wire-shape; trace instrumentation visible end-to-end. | Demo endpoints replaced by real product methods; metric surface added once chosen. |
| Server → metrics DB | mTLS (mutual TLS), certificates injected by the catalogue's secrets layer. | Worked example of the inter-service mTLS pattern. | File-mounted certs replaced by mesh-issued short-lived identities. |
| www | Next.js front-end, traces enabled, dashboard panels embedded inline. | Pages, API routes, middleware all emit traces; Grafana owns dashboard chrome. | Iframe embeds wrapped by an auth gateway. |
| gRPC load balancing | Next.js backend calls Rust directly, server-side. | Browser → HTTPS → Next.js → gRPC → Rust. The gRPC hop stays server-side. | Mesh-aware LB (Load Balancer) or grpc-web bridge. |
| Wire schema | Single `.proto` shared between Rust and Next.js. | One language commits generated code; the other loads at runtime. | Real product schema; lint + breaking-change tooling layered on top. |
| Local mTLS setup | `make mtls` generates a dev CA (Certificate Authority) + per-service keys into a gitignored dir. | One command, zero friction; certs bind-mounted into containers. | Replaced by a real secrets backend. |
| Secrets injection | Compose labels turn env vars into K8s (Kubernetes) Secrets and mount cert files. | Team-facing interface stays compose; the chart generates the right Secret/ConfigMap shapes. | Same interface; secrets resolve from a real backend. |
| Volume classes | Named local volume in dev; chart exposes a storage-class values field. | Dev doesn't need named classes; each env overlays the right one. | Named classes (`soc2_sensitive`, etc.) provisioned by the cluster. |
| Containers | Single-stage Dockerfiles for Rust and Next.js; everything else off-the-shelf. | Shortest build path; hardening costs build time without demo value. | Multi-stage, non-root, real healthchecks, signed images. |
| Image tags | Hardcoded placeholder. | The Helm generator needs a tag; no registry to push to locally. | CI-derived tag pushed with provenance + SBOM (Software Bill of Materials). |
| Compose-to-Helm labels | Standard label set from [`katenary-top-seven.md`](../engineering/rules/katenary-top-seven.md). Includes `katenary.v3/ports` on any port-less service that other services `depends_on` (cadvisor, node-exporter) — without it katenary can't generate the readiness init-container and chart-gen exits non-zero (upstream issue #182). Pre-commit regenerates the chart when compose or catalogue YAML changes. | Each label flips one specific compose→Helm translation. | May extend with org-specific custom labels. |
| README scope | `docker compose up`; runs in GitHub Codespaces per the take-home requirements. | Codespaces is the most predictable demo environment for reviewers. | Deployment runs via the org's standard CI/CD. |
| Live demo | CloudFlare Zero Trust tunnel + Access to author's K8s cluster. | Easy public URL with an auth gate; no warranty for other clusters. | Real ingress with cert-manager + org IdP (Identity Provider). |
| Logging | `logging/` catalogue module — Loki 3.x + collector's filelog receiver tailing the docker JSON log driver. App containers emit the cross-language structured-log contract (next row); the filelog json_parser extracts contract fields and the collector promotes the OTel-canonical identity (`service.name`, `service.namespace`, `service.instance.id`, `deployment.environment.name`) plus project attrs (`module_name`, `owned_by`) and `level` to Loki indexed labels. `service` (no dot) survives as an alias of `service.name`, set in the same filelog pipeline so existing JSON-stdout sources keep their label and OTel-canonical dashboards see `service_name`. `container_id`, `trace_id`, `span_id` ride as structured metadata (host- and trace-scoped — fast to query, no cardinality cost). Non-conforming sources (postgres, otel-collector, grafana, etc.) reach Loki with empty contract fields — the imported APM dashboard's stream selectors filter them out at any service filter (intentional scope: that dashboard is for app traffic). Per-source extractors are the prod-considerations item. | Single ingestion path covers every container without per-app instrumentation. The k8s overlay swaps the include path to `/var/log/containers/*.log` — same receiver, different glob. Indexed labels are bounded-cardinality dimensions; high-cardinality fields stay as structured metadata. | Managed Loki / cloud logging backend; PII redaction processor; per-source extractors for non-app containers so they conform to the same label/level contract — either docker_observer enrichment or per-format filelog operators. |
| Structured-log contract | App containers (server, www) emit one JSON object per stdout line: `timestamp` (RFC 3339 UTC ms), `level` (lowercase enum: `trace`/`debug`/`info`/`warn`/`error`/`fatal`), `service` (matches `metrics.service_name`), `message`, `trace_id` + `span_id` (lowercase hex W3C, when an OTel span is active), `module_name` + `owned_by` (from `OTEL_RESOURCE_ATTRIBUTES`), plus free-form extras. Rust: `tracing-subscriber::fmt::layer().json()` with a process-wide root span carrying the contract fields; the collector's filelog operators flatten the nested `attributes.span.*` keys before promoting them. www: Pino with `base: { service, module_name, owned_by }` and a custom `log` formatter that injects active OTel context. Collector lowercases `level` so Rust + Pino agree. | Forces one shape across languages, so the logs panel filters work whatever the source language. Non-conforming containers pass through with empty contract fields. | Cross-source extractors (per-format filelog operators for postgres / grafana / collector / etc.) so infra containers conform to the same label/level surface. Validate `level` enum at the collector to bound Loki label cardinality. |
| Bonuses | All six items from `requirements.md` in scope. | OTel (OpenTelemetry)-everywhere carries logging and error handling; catalogue argument carries data design. | Per-bonus mapping in the spec. |
| Catalog wire shape | AIP-130 standard methods on DataSource (read-only) and Dashboard (full CRUD); tagged-union panel body (Timeseries/Stat/Table). Paths only — www prepends `NEXT_PUBLIC_GRAFANA_URL`. | Symmetric resource shape per AIP; client-side URL composition keeps the server environment-agnostic. | Add `page_size`/`page_token` (AIP-158) if data sets grow. |
| Grafana auth | Static service-account token, env-injected. Dev: `make setup` runs `docker compose down -v` (sledgehammer reset — wipes all volumes), then mints a fresh token via the profile-gated `grafana-bootstrap` one-shot. Side-stepping persisted-state drift is cheaper than a granular reset path for a take-home. | Production-shaped credential (Grafana 9+ replaces API keys with service accounts); single token, Bearer header. | Granular per-catalogue-item setup tasks (each runnable with `--force`); replace `grafana-bootstrap` with a Vault Agent / secrets-backend sidecar that writes the same file. Rust code unchanged. |

### Process notes (not architecture)

- **Tests:** Rust unit/integration in `server/`; Next.js tests in `www/`. High-value tests only — PoC (Proof of Concept) scope.
- **Commit hygiene:** test changes and code changes never share a commit; code commits require a green tree.

## Open

V0 questions still in flux. Production-scope questions live in [`PRODUCTION_DISCUSSIONS.md`](./PRODUCTION_DISCUSSIONS.md).

- **mTLS demonstration depth.** Minimum: server logs successful connection at startup. Reviewer-visible: on-demand gRPC method + UI button.
- **Collector → TSDB mTLS on the dev path.** Plain HTTP for now; uniform with the Rust→TSDB hop is possible at small cost.
- **Outbound client metrics.** Apps now emit OTel-semconv server metrics (`rpc.server.duration` from the Rust tower middleware; `http.server.request.duration` from `@opentelemetry/instrumentation-http` in www) — those land the RED rows on the imported APM dashboard. Outbound client metrics (`http.client.duration`, `db.client.duration`, `rpc.client.duration`) are still partial: Node's auto-instrumentation emits HTTP-client metrics by default; the Rust client paths (reqwest → Grafana, sqlx → postgres, tonic-client from www-as-grpc-client) need explicit instrumentation. Outbound panels on the dashboard stay sparse until that lands.
- **Panel types beyond Timeseries.** Stat and Table variants stubbed in `metrics.proto` — handler returns `UNIMPLEMENTED`. Wired when a reviewer use-case appears; panel JSON differs only in `type` + a couple of option fields per type, so it's mostly mechanical.

## Deviations from `requirements.md`

- **Agent → Server arrow is layered.** Off-the-shelf collector receives; TSDB stores; Rust server is the application API in front. *"The server"* in the requirements' sense is the layered tier.
- **Server in Rust** — satisfies the literal requirement.
- **Agent in Python** (Tasks section) — superseded by Core Requirements' "any language." Off-the-shelf collector instead, packaged as a catalogue module.
