# Design decisions

Current state of every design choice — one row each. Implementation specifics (crates, code layout, label syntax) live in [`docs/engineering/`](../engineering/) and the spec at [`docs/superpowers/specs/`](../superpowers/specs/).

Companion: [`ENGINEERING_RULES.md`](./ENGINEERING_RULES.md), [`PROJECT_SCOPE.md`](./PROJECT_SCOPE.md), [`PRODUCTION_DISCUSSIONS.md`](./PRODUCTION_DISCUSSIONS.md).

This repo is a reference implementation of the **microservice-template + service-catalogue pattern** — the design pattern that becomes [LocalMesh](../../README.md) once an org's SRE-owned plugins are in place. The Rust + Next.js parts are one team's microservice; observability, logging, `caddy` (north-south ingress), `auth_shim` (dev user picker), and the optional database are catalogue modules the team includes from a stub catalogue.

## Starting assumptions

Every decision below sits on top of these. They are not design choices — they are the premises the pattern only works under.

- **Mandatory tools have to be easier to use than to work around.** If using the supported path is harder than disabling, bypassing, or stubbing it, the supported path loses. Applies universally — to SRE plugins, test frameworks, linters, security controls, anything anyone is told they have to use. Adoption depends on the easier path being the supported one.
- **Compose is the limit of what a non-ops team handles on their own.** Helm is too much; bare k8s manifests are too much. Compose is the dev-facing interface every team already touches; the prescriptive middle layer (the chart generator) shifts that workload off per-team toil and onto larger infra and catalogue investments.
- **Production-quality on dev becomes production.** Each catalogue module ships the same shape ops would run in prod, just locally-hosted. Dev gets the *real* observability stack, the *real* logging contract, the *real* identity tuple — the prod overlay swaps storage backends and the rest is the same wire. Drift between dev and prod is the single most expensive failure mode of any platform pattern; this is the structural fix.
- **One human-scale file holds the cross-stakeholder truth.** [`project.toml`](../../project.toml) is where team work, SRE oversight, and business requirements intersect — identity, compliance flags, data residency, billing, ownership — auditable at whatever level the context demands. Compliance, legal, billing, and ops all read the same file; engineering decisions don't get translated into business language.
- **The compose→helm boundary is strict on purpose.** Teams own everything inside their compose; SRE owns everything past the helm chart. The framework is opinionated on the translation in between and hands-off about what SRE puts on either side.

| Dashboards | Module-as-contributor pattern. Every module that ships a dashboard drops `<slug>.json` next to its `docker-compose.yml`, declares it via a top-level `configs:` entry keyed `<module>_dashboard_<slug>`, and mounts it onto the `grafana` service at `/etc/grafana/dashboards/<module>/<slug>.json`. Compose's `include:` merge unions `services.grafana.configs:` across all included modules so the destination Grafana sees every contribution automatically — no central registry, no coordination. Grafana's file provider runs with `foldersFromFilesStructure: true` so each `<module>/` subdir becomes a UI folder; `allowUiUpdates: true` for now so devs can iterate in the UI without friction. Observability is just another module that happens to host the Grafana runtime — its dashboards (`observability/apm.json`, `observability/cluster-health.json`) use the same contribution pattern. The runtime (image, datasources, provisioning config, bootstrap script) stays in observability's compose; no other module touches it. **`apm`** — imported community dashboard "[Lightweight APM for OpenTelemetry](https://grafana.com/grafana/dashboards/22784)" (Grafana ID 22784, [source](https://github.com/cyrille-leclerc/opentelemetry-service-dashboard)); patched: datasource defaults bound to our UIDs, template-variable queries source from `label_values(LABEL)` directly (VM doesn't have `keep_identifying_resource_attributes`), stat-panel filters use `job=~"$service_namespace/$service_name"`. **`cluster-health`** — host/container resources (cadvisor + node-exporter) plus a module-roster panel. **`postgres`** (database module, worked example) — community dashboard [9628](https://grafana.com/grafana/dashboards/9628) by Lucas Estienne, patched for our datasource UIDs + label conventions; adds one custom top-N slow-query table panel sourced from `pg_stat_statements`. Database's compose also ships a `postgres-exporter` sidecar (emits metrics) and a `database-collector` sidecar (scrapes the exporter, pushes OTLP to the main otel-collector). **`ingress`** (caddy module) — request rates by HTTP status, p50/p95 ingress latency, upstream health; sourced from Caddy access logs via Loki. Custom — no upstream community dashboard fits the Caddy-as-mesh-ingress shape. Long form: [`docs/superpowers/specs/2026-05-17-module-dashboards-design.md`](../superpowers/specs/2026-05-17-module-dashboards-design.md). | Destination Grafana auto-discovers contributions the moment a module is `include:`d. Modules stay self-contained and removable. Importing community dashboards validates the omakase contract — if they work against this stack, they work against any OTel-conforming stack. | Harden to `allowUiUpdates: false` once the pattern is stable. Extend the same pattern to alert/recording rules (`<module>.alerts.yaml` mounted under `/etc/grafana/alerting/<module>/`). When a metrics module needs cross-module scrape contribution to the main collector, use a sidecar collector pattern (spec §6.3 — chosen here because `otel-collector-contrib:0.152.0` doesn't ship the `glob:` config provider the multi-config-merge alternative would need). |
| Module observability conventions | Compose config key naming: `<module>_dashboard_<slug>` for dashboards; `<module>_<purpose>` for other configs (e.g., `database_collector_config`, `database_pgexporter_queries`). Grafana mount target: `/etc/grafana/dashboards/<module>/<slug>.json` — the intermediate `<module>/` subdir is what triggers `foldersFromFilesStructure` to create a UI folder. For modules that emit metrics: ship a per-module sidecar collector that scrapes the module's emitters and pushes OTLP to the main collector at `otel-collector:4317`. Stamps the standard identity tuple via the OTel resource processor (`service.name`, `module_name`, `owned_by`) — convention now canonical in [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md). Zero cross-module config coordination — each module is self-contained. | Pattern is uniform across modules; observability owns the runtime, modules own their data. | Revisit the sidecar-vs-overlay decision if a future collector image ships the `glob:` config provider — then the single-collector-with-overlay approach (spec §6.3) becomes viable and might be preferred for runtime efficiency. |
| Module attribution | Every application signal carries the OTel-canonical identity tuple — `service.name`, `service.namespace`, `service.instance.id`, `deployment.environment.name` — plus the two project-specific attrs `module_name` and `owned_by`. For traces and metrics, identity flows through `OTEL_SERVICE_NAME` + `OTEL_RESOURCE_ATTRIBUTES` env vars consumed by the OTel SDK at startup. The Rust SDK reads both; `@vercel/otel` (www) does the same; pg_tracing's hardcoded `service.name=PostgreSQL_Server` gets rewritten by the collector's `transform/database`. For logs, identity is supplied by Vector at ingest from the per-service `metrics.service_name` / `metrics.module_name` / `metrics.owned_by` docker labels — apps emit none of these in their stdout. Resource attrs become labels on every series (collector's `resource_to_telemetry_conversion`) and indexed Loki labels (config in `service_catalog/logging/`). Cadvisor's `metrics.service_name` docker label still becomes a `service` (lowercase) metric label — kept as a *container-resource* lens distinct from the application-identity tuple; the two coexist intentionally. `service.namespace` tracks `${PROJECT_NAME}` (from `.env`, mirroring `project.toml`) so compose `name:` and OTel namespace share one source. The identity-tuple binding (`module_name=app` vs. `<plugin-slug>`) is canonical in [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md). Two channels for the same identity (compose env for SDK, docker labels for Vector) is a known duplication — single-source consolidation is a follow-up (see Open). | One identity tuple makes the roster, RED, and owner-attribution queryable across all three signals. The OTel-canonical attrs are what the imported APM dashboard (and every off-the-shelf OTel dashboard) reads. | `owned_by` resolves from the org's team registry rather than hardcoded compose values; `service.namespace` becomes the team/tenant axis. |
| Database module (optional) | Postgres 16 + Datadog's `pg_tracing` extension, custom-built image, OTLP/HTTP push to the collector. Hard-coded sampling at 1.0; `service.name` rewritten `PostgreSQL_Server` → `postgres` at the collector. Server holds a `sqlx` `PgPool` plumbed via `DATABASE_URL`; `sqlx::migrate!()` applies embedded SQL migrations at server startup. Demo `Greeter.PrintPostgresStats` RPC writes one `noise_events` row per click and reads the five headline `pg_stat_database` metrics; each SQL statement carries a `/*traceparent='...'*/` comment so pg_tracing stitches the resulting parse/plan/exec spans under the gRPC server span. Real product use-cases (registry / audit log / events) deferred — they'll define their own schemas alongside `noise_events`. Rollbacks deliberately out of scope: "rollback" means different things across prod targets (managed-DB point-in-time-restore vs. compensating migrations vs. blue/green schema flips); `sqlx::migrate!()` doesn't preclude any of them. | Single image, zero polling glue — pg_tracing emits parse/plan/exec spans as children of any traceparent embedded as a SQL comment, so the trace `user → www → server → postgres` works end-to-end without per-team integration code. | Managed offering (RDS / CloudSQL) with pg_tracing enabled via parameter group; sampling tuned to ~1-5%. | Server → metrics DB | Native postgres mTLS. `postgresql.conf` reads `id.postgres.{crt,key}` + `trust.ca.crt` from the per-plugin cert mount; `pg_hba.conf` enforces `hostssl … cert clientcert=verify-full` with the role `server` cert-CN-bound. | LocalMesh CA bootstrap | `make certs` runs `scripts/secrets-gen.py` — reads `project.toml` + every `service_catalog/*/plugin.toml`, mints the LocalMesh CA + per-service leaf certs into `.secrets/certs/<container>/{trust.ca.crt,id.crt,id.key}`, regenerates `.env` (managed section: every TOML field as UPCASE_SNAKECASE for compose interpolation), and emits `service_catalog/caddy/Caddyfile.generated` with one site block per `[[services]]` entry whose `expose_via_ingress = true`. Host trust install via `step certificate install` (cross-platform). `make certs` always wipes and regenerates — no granular subcommand (out of scope for a take-home). The existing `make setup` target (grafana-token bootstrap) chains `certs` and is otherwise unchanged. | Single command bootstraps the entire mesh's identity surface from declarative TOML. New plugins drop a `plugin.toml`, re-run `make certs`, get certs + Caddy routes + env-var bindings for free. | Logging platform contract | Stack-agnostic event envelope (one NDJSON event per stdout line: `timestamp` / `level` / `message` / `trace_id`+`span_id` when an OTel span is active / free-form attributes); three-tier cardinality contract (indexed labels for bounded dimensions, structured metadata for high-cardinality queryable fields, body for free text); the agent owns parse, enrich, validate, redact, sample, batch. Per-language emitter recipes (`tracing` + `tracing-subscriber` + `tracing-opentelemetry` for Rust, Pino + `@opentelemetry/api` for Node) and per-source agent extractor recipes (postgres jsonlog, nginx, grafana logfmt, etc.) keep teams omakase-conformant with minimal effort. Long form: [`docs/engineering/rules/logging-platform.md`](../engineering/rules/logging-platform.md). | Vendor-portable across Loki, Datadog, Splunk, Honeycomb, Elastic, GCP / AWS cloud logging — the envelope is the OTel logs data model and the cardinality contract is the same wherever you put it. Apps install one package and copy 5 lines; SREs extend the agent's job as far as they care to. | Per-source extractor verification for unfamiliar emitters; PII redaction processor wired in at the agent; per-environment retention + sampling tiers. |
| Logging | `logging/` catalogue module — Loki 3.x for storage, Vector 0.46 for ingest. Vector's `docker_logs` source tails the docker socket and exposes container labels on every event; a VRL `enrich` transform promotes `metrics.service_name` / `metrics.module_name` / `metrics.owned_by` to event fields. `parse_envelope` reads the app JSON contract out of `.message` (non-conforming sources fall through unchanged). A `route` transform splits by source: postgres jsonlog → `norm_postgres` (`error_severity` → contract `level` enum), grafana logfmt → `norm_grafana` (lvl → level + message extraction), everything else → `norm_default` (defaults `level=info`). A `validate` remap lowercases `level` and drops any out-of-enum value so Loki's label cardinality stays bounded. The `loki` sink ships indexed labels (service_name / module_name / owned_by / deployment_environment_name / level / container_id) and trace_id / span_id as structured metadata. otel-collector owns traces + metrics only — no filelog receiver, no loki exporter. K8s overlay swaps `docker_logs` → `kubernetes_logs` (VRL `.label.*` becomes `.kubernetes.pod_labels.*`); the rest carries over. Long form: [`docs/superpowers/specs/2026-05-17-logging-platform-contract-design.md`](../superpowers/specs/2026-05-17-logging-platform-contract-design.md). | Single agent owns the log path. Apps emit the envelope and nothing else; the agent supplies identity from container labels; severity is bounded at ingest so Loki labels stay bounded. Backend swap (Datadog / Splunk / managed Loki) means changing the sink, nothing else. | Managed Loki backend; per-source remaps for the no-op-default sources when SREs want severity filtering on them; PII redaction processor wired upstream of the sink; per-environment sampling tiers. |
| Structured-log contract | App containers (server, www) emit one JSON object per stdout line: `timestamp` (RFC 3339 UTC ms), `level` (lowercase enum: `trace`/`debug`/`info`/`warn`/`error`/`fatal`), `message`, `trace_id` + `span_id` (lowercase hex W3C, when an OTel span is active), plus free-form extras. Resource attributes (`service.name`, `module_name`, `owned_by`, `deployment.environment.name`) are **not** in the envelope — the Vector agent supplies them from container labels (next row). Rust: `tracing-subscriber::fmt::layer().json()` + `tracing-opentelemetry` bridge; root span is just `tracing::info_span!("app")`. The `ErrorLogLayer` Tower middleware logs non-OK gRPC `Status` returns at WARN/ERROR with `trace_id` and `span_id` pulled from the active OTel span (the JSON formatter doesn't auto-bridge those into event records). www: Pino with no `base:` block; `formatters.log` injects active OTel context. Per-language emitter recipes for other stacks (Go / Python / JVM / Ruby / .NET) live in the rules doc. | Apps stay dumb. Same JSON shape across languages. Conforming costs one package + 5 lines of init. | Per-language recipe verification for the four unverified rows when a service in any of those languages joins the catalogue. |
| Bonuses | All six items from `requirements.md` in scope. | OTel (OpenTelemetry)-everywhere carries logging and error handling; catalogue argument carries data design. | Per-bonus mapping in the spec. |

| Grafana auth | Static service-account token, env-injected. | Service mesh — local model | `caddy` plugin provides north-south HTTPS ingress with hostname routing (`https://<container>.${PROJECT_NAME}.${LOCAL_DOMAIN}:8443`). East-west is in-process native mTLS — `tonic-rustls` in the Rust server, `https.createServer` + `@grpc/grpc-js` SSL in www, native `postgresql.conf` mTLS in postgres. Identity-of-record is a SPIFFE URI in every cert SAN. Verification is verify-CA at the rustls / Node layers; verify-full + CN-to-role binding at the postgres layer. Observability containers are mesh-exempt (`mesh.exempt: "true"` compose label; no certs minted). The `auth_shim` plugin (dev-only user picker) is also mesh-exempt; oauth2-proxy + a real IdP replaces it in prod. | The mesh isn't a single plugin — it's the SRE-prescribed default that every workload participates in. `caddy` is the dev incarnation of a real ingress controller; in-process east-west mirrors how a sidecar-less polyglot mesh (linkerd-proxy or Cilium eBPF) actually delivers identity. | Workload identity (SPIFFE shape) | Every workload holds one bidirectional cert (`server-`+`clientAuth` EKU) at `.secrets/certs/<container>/`. CN = container name; SPIFFE URI SAN = `spiffe://<container>.${PROJECT_NAME}.${LOCAL_DOMAIN}`; DNS SANs cover the bare container name + the wildcard `<container>.${PROJECT_NAME}.${LOCAL_DOMAIN}`; IP SANs are intentionally over-permissive in dev. `plugin.toml` lists `[[services]]` entries (`container`, `port`, `expose_via_ingress`, `ingress`) per workload the plugin owns. Server's `peer_interceptor` reads tonic's `TlsConnectInfo` extension → extracts the SPIFFE URI via `x509-parser` → inserts a `PeerIdentity` extension; handlers read it for business logic (e.g., the WhoAmI response field) but do not stamp it on OTel spans. | One identity per workload, bidirectional, SPIFFE-faithful. Identity-of-record matches what SPIRE will issue in prod. | SVIDs minted on demand by SPIRE; short-lived (~1h); rotated automatically. Bidirectional EKU stays. IP SAN list drops to nothing (prod uses DNS-based identity exclusively). |
| Trusted localdev TLS | LocalMesh CA installed into the host trust store via `step certificate install`. Browser hits `https://<container>.${PROJECT_NAME}.${LOCAL_DOMAIN}:8443` with no warning and the green padlock. `${LOCAL_DOMAIN}` defaults to `lvh.me` (magic DNS — every subdomain resolves to 127.0.0.1) so no `/etc/hosts` editing is needed; `local_domain` in `project.toml` overrides if a real local DNS is preferred. Wildcard cert SAN (`*.${PROJECT_NAME}.${LOCAL_DOMAIN}`) on the Caddy ingress so adding a new exposed UI doesn't need a re-mint. | The whole "is this cert trusted?" debate gets resolved at `make setup` time. `step` is purpose-built for cross-platform trust store registration; vendoring it removes the host-install prerequisite. lvh.me removes the last "sudo on first run" step. Wildcard cert in dev is convenient and explicitly TODO'd against prod. | Real internal DNS + cert-manager-issued IngressRoute certs at the cluster ingress. Per-host certs (no wildcards) in prod. |
| User identity at ingress | www stamps `enduser.id` / `enduser.email` (plus legacy mirror `user.id` / `user.email`) on the active OTel span at the entry point of each API route. This is the only place PII lands in telemetry — downstream services (`server`, `postgres`) receive user identity via `x-user-*` gRPC metadata into request extensions for business-logic use but do not echo PII onto their own spans or indexed Loki labels.
