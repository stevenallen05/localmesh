# Design decisions

Current state of every design choice — one row each. Implementation specifics (crates, code layout, label syntax) live in [`docs/engineering/`](../engineering/) and the spec at [`docs/superpowers/specs/`](../superpowers/specs/).

Companion: [`ENGINEERING_RULES.md`](./ENGINEERING_RULES.md), [`PROJECT_SCOPE.md`](./PROJECT_SCOPE.md), [`PRODUCTION_DISCUSSIONS.md`](./PRODUCTION_DISCUSSIONS.md).

This repo is a reference implementation of the **microservice-template + service-catalogue pattern** — the design pattern that becomes [LocalMesh](../../README.md) once an org's SRE-owned plugins are in place. The Rust + Next.js parts are one team's microservice; observability, logging, `auth` (dex IdP), and the optional database are catalogue modules the team includes from a stub catalogue.

## Starting assumptions

Every decision below sits on top of these. They are not design choices — they are the premises the pattern only works under.

- **Mandatory tools have to be easier to use than to work around.** If using the supported path is harder than disabling, bypassing, or stubbing it, the supported path loses. Applies universally — to SRE plugins, test frameworks, linters, security controls, anything anyone is told they have to use. Adoption depends on the easier path being the supported one.
- **Compose is the limit of what a non-ops team handles on their own.** Helm is too much; bare k8s manifests are too much. Compose is the dev-facing interface every team already touches; the prescriptive middle layer (the chart generator) shifts that workload off per-team toil and onto larger infra and catalogue investments.
- **Production-quality on dev becomes production.** Each catalogue module ships the same shape ops would run in prod, just locally-hosted. Dev gets the *real* observability stack, the *real* logging contract, the *real* identity tuple — the prod overlay swaps storage backends and the rest is the same wire. Drift between dev and prod is the single most expensive failure mode of any platform pattern; this is the structural fix.
- **One human-scale file holds the cross-stakeholder truth.** [`project.toml`](../../project.toml) is where team work, SRE oversight, and business requirements intersect — identity, compliance flags, data residency, billing, ownership — auditable at whatever level the context demands. Compliance, legal, billing, and ops all read the same file; engineering decisions don't get translated into business language.
- **The compose→helm boundary is strict on purpose.** Teams own everything inside their compose; SRE owns everything past the helm chart. The framework is opinionated on the translation in between and hands-off about what SRE puts on either side.

## Settled

| Vision | One team's microservice + a stub catalogue module. | Demonstrates the org-scale pattern: platform owns catalogue, product owns compose. | Catalogue becomes a real platform product. |
| Orchestration | Compose is source of truth; pre-commit hook generates the Helm chart. | Compose is the practical ceiling for self-service teams; chart is build output. | Chart generation runs in CI; published to an internal registry. |

| OTel semconv as the omakase contract | Apps follow OpenTelemetry semantic conventions end-to-end: standard env vars (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`, `OTEL_SEMCONV_STABILITY_OPT_IN=http` for Node); standard metric names (`http.server.request.duration`, `rpc.server.duration`); standard resource attrs promoted to series labels (`service_name`, `service_namespace`, `service_instance_id`, `deployment_environment_name`). Single bootstrap per language: Rust extends `server/src/telemetry.rs` with a `MeterProvider` + `RpcMetricsLayer` tower middleware; Node extends `www/instrumentation.ts` with `HttpInstrumentation` + a `PeriodicExportingMetricReader` via `@vercel/otel`. Collector translates OTel→Prometheus on VM's behalf (`prometheusremotewrite` exporter with `resource_to_telemetry_conversion`); VM has an OTLP receiver but lacks `keep_identifying_resource_attributes`, which the imported dashboard's header stat panels need — the collector path supplies it. Long form: [`docs/superpowers/specs/2026-05-16-otel-semconv-pipeline-design.md`](../superpowers/specs/2026-05-16-otel-semconv-pipeline-design.md). | One env-var convention + one bootstrap file per language gives any new service the canonical OTel dashboard for free. Backend swaps (Mimir / Grafana Cloud / Prometheus 3.x with OTLP receiver) need only the resource-attr promotion knob flipped — apps and dashboards portable. | Add OTLP semconv metrics for outbound HTTP / DB / RPC clients (currently only the Node SDK auto-emits these); add `service.version` from build metadata. |
| Module observability conventions | Compose config key naming: `<module>_dashboard_<slug>` for dashboards; `<module>_<purpose>` for other configs (e.g., `database_collector_config`, `database_pgexporter_queries`). Grafana mount target: `/etc/grafana/dashboards/<module>/<slug>.json` — the intermediate `<module>/` subdir is what triggers `foldersFromFilesStructure` to create a UI folder. Two metric-contribution patterns. Pattern B (sidecar push) — for modules that emit metrics: ship a per-module sidecar collector that scrapes the module's emitters and pushes OTLP to the main collector at `otel-collector:4317`. Stamps the standard identity tuple via the OTel resource processor (`service.name`, `module_name`, `owned_by`) — convention now canonical in [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md). Pattern A (centrally scraped emitters) is label-based discovery. The main collector's prometheus receiver uses `docker_sd_configs` with relabel rules keyed on `prometheus.io/scrape=true` + `prometheus.io/port` (+ optional `prometheus.io/path`) container labels. Cross-plugin edits to observability's collector config are no longer needed for new Pattern-A targets. Pattern B stays for plugins with rich scrape config the labels can't express (e.g., postgres-exporter's custom queries file). Zero cross-module config coordination — each module is self-contained. | Pattern is uniform across modules; observability owns the runtime, modules own their data. | Revisit the sidecar-vs-overlay decision if a future collector image ships the `glob:` config provider — then the single-collector-with-overlay approach (spec §6.3) becomes viable and might be preferred for runtime efficiency. |
| Module attribution | Every application signal carries the OTel-canonical identity tuple — `service.name`, `service.namespace`, `service.instance.id`, `deployment.environment.name` — plus the two project-specific attrs `module_name` and `owned_by`. For traces and metrics, identity flows through `OTEL_SERVICE_NAME` + `OTEL_RESOURCE_ATTRIBUTES` env vars consumed by the OTel SDK at startup. The Rust SDK reads both; `@vercel/otel` (www) does the same; pg_tracing's hardcoded `service.name=PostgreSQL_Server` gets rewritten by the collector's `transform/database`. For logs, identity is supplied by Vector at ingest from the per-service `metrics.service_name` / `metrics.module_name` / `metrics.owned_by` docker labels — apps emit none of these in their stdout. Resource attrs become labels on every series (collector's `resource_to_telemetry_conversion`) and indexed Loki labels (config in `service_catalog/logging/`). Cadvisor's `metrics.service_name` docker label still becomes a `service` (lowercase) metric label — kept as a *container-resource* lens distinct from the application-identity tuple; the two coexist intentionally. `service.namespace` tracks `${PROJECT_NAME}` (from `.env`, mirroring `project.toml`) so compose `name:` and OTel namespace share one source. The identity-tuple binding (`module_name=app` vs. `<plugin-slug>`) is canonical in [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md). Two channels for the same identity (compose env for SDK, docker labels for Vector) is a known duplication — single-source consolidation is a follow-up (see Open). | One identity tuple makes the roster, RED, and owner-attribution queryable across all three signals. The OTel-canonical attrs are what the imported APM dashboard (and every off-the-shelf OTel dashboard) reads. | `owned_by` resolves from the org's team registry rather than hardcoded compose values; `service.namespace` becomes the team/tenant axis. |
| Database module (optional) | Postgres 16 + Datadog's `pg_tracing` extension, custom-built image, OTLP/HTTP push to the collector. Hard-coded sampling at 1.0; `service.name` rewritten `PostgreSQL_Server` → `postgres` at the collector. Server holds a `sqlx` `PgPool` plumbed via `DATABASE_URL`; `sqlx::migrate!()` applies embedded SQL migrations at server startup. Demo `Greeter.PrintPostgresStats` RPC writes one `noise_events` row per click and reads the five headline `pg_stat_database` metrics; each SQL statement carries a `/*traceparent='...'*/` comment so pg_tracing stitches the resulting parse/plan/exec spans under the gRPC server span. Real product use-cases (registry / audit log / events) deferred — they'll define their own schemas alongside `noise_events`. Rollbacks deliberately out of scope: "rollback" means different things across prod targets (managed-DB point-in-time-restore vs. compensating migrations vs. blue/green schema flips); `sqlx::migrate!()` doesn't preclude any of them. | Single image, zero polling glue — pg_tracing emits parse/plan/exec spans as children of any traceparent embedded as a SQL comment, so the trace `user → www → server → postgres` works end-to-end without per-team integration code. | Managed offering (RDS / CloudSQL) with pg_tracing enabled via parameter group; sampling tuned to ~1-5%. Migration-rollback strategy chosen alongside the prod DB target. |
| Server → metrics DB | Native postgres mTLS. `postgresql.conf` reads `id.postgres.{crt,key}` + `trust.ca.crt` from the per-plugin cert mount; `pg_hba.conf` enforces `hostssl … cert clientcert=verify-full` with the role `server` cert-CN-bound. Rust client (sqlx + tls-rustls) reads `id.server.{crt,key}` for outbound. No password fallback. `postgres-exporter` joins the mesh too with its own cert + role. Postgres and exporter both wrap their image entrypoints to copy bind-mounted certs into a postgres-owned location with `0600` .key (`pq` and postgres itself enforce strict perms). | Worked example of the inter-service mTLS pattern landed end-to-end: cert + chain + CN-to-role binding all real. | File-mounted certs replaced by SPIRE-issued short-lived SVIDs delivered via cert-manager / Workload API; pg-side strict-perm gymnastics goes away. |
| Wire schema | Single `.proto` shared between Rust and Next.js. | One language commits generated code; the other loads at runtime. | Real product schema; lint + breaking-change tooling layered on top. |
| Volume classes | Named local volume in dev; chart exposes a storage-class values field. | Dev doesn't need named classes; each env overlays the right one. | Named classes (`soc2_sensitive`, etc.) provisioned by the cluster. |
| Containers | Single-stage Dockerfiles for Rust and Next.js; everything else off-the-shelf. | Shortest build path; hardening costs build time without demo value. | Multi-stage, non-root, real healthchecks, signed images. |
| Image tags | Hardcoded placeholder. | The Helm generator needs a tag; no registry to push to locally. | CI-derived tag pushed with provenance + SBOM (Software Bill of Materials). |
| Compose-to-Helm labels | Standard label set from [`katenary-top-seven.md`](../engineering/rules/katenary-top-seven.md). Includes `katenary.v3/ports` on any port-less service that other services `depends_on` (cadvisor, node-exporter) — without it katenary can't generate the readiness init-container and chart-gen exits non-zero (upstream issue #182). Pre-commit regenerates the chart when compose or catalogue YAML changes. | Each label flips one specific compose→Helm translation. | May extend with org-specific custom labels. |
| README scope | `docker compose up`; runs in GitHub Codespaces per the take-home requirements. | Codespaces is the most predictable demo environment for reviewers. | Deployment runs via the org's standard CI/CD. |
| Live demo | CloudFlare Zero Trust tunnel + Access to author's K8s cluster. | Easy public URL with an auth gate; no warranty for other clusters. | Real ingress with cert-manager + org IdP (Identity Provider). |
| Logging platform contract | Stack-agnostic event envelope (one NDJSON event per stdout line: `timestamp` / `level` / `message` / `trace_id`+`span_id` when an OTel span is active / free-form attributes); three-tier cardinality contract (indexed labels for bounded dimensions, structured metadata for high-cardinality queryable fields, body for free text); the agent owns parse, enrich, validate, redact, sample, batch. Per-language emitter recipes (`tracing` + `tracing-subscriber` + `tracing-opentelemetry` for Rust, Pino + `@opentelemetry/api` for Node) and per-source agent extractor recipes (postgres jsonlog, nginx, grafana logfmt, etc.) keep teams omakase-conformant with minimal effort. Long form: [`docs/engineering/rules/logging-platform.md`](../engineering/rules/logging-platform.md). | Vendor-portable across Loki, Datadog, Splunk, Honeycomb, Elastic, GCP / AWS cloud logging — the envelope is the OTel logs data model and the cardinality contract is the same wherever you put it. Apps install one package and copy 5 lines; SREs extend the agent's job as far as they care to. | Per-source extractor verification for unfamiliar emitters; PII redaction processor wired in at the agent; per-environment retention + sampling tiers. |
| Logging | `logging/` catalogue module — Loki 3.x for storage, Vector 0.46 for ingest. Vector's `docker_logs` source tails the docker socket and exposes container labels on every event; a VRL `enrich` transform promotes `metrics.service_name` / `metrics.module_name` / `metrics.owned_by` to event fields. `parse_envelope` reads the app JSON contract out of `.message` (non-conforming sources fall through unchanged). A `route` transform splits by source: postgres jsonlog → `norm_postgres` (`error_severity` → contract `level` enum), grafana logfmt → `norm_grafana` (lvl → level + message extraction), everything else → `norm_default` (defaults `level=info`). A `validate` remap lowercases `level` and drops any out-of-enum value so Loki's label cardinality stays bounded. The `loki` sink ships indexed labels (service_name / module_name / owned_by / deployment_environment_name / level / container_id) and trace_id / span_id as structured metadata. otel-collector owns traces + metrics only — no filelog receiver, no loki exporter. K8s overlay swaps `docker_logs` → `kubernetes_logs` (VRL `.label.*` becomes `.kubernetes.pod_labels.*`); the rest carries over. Long form: [`docs/superpowers/specs/2026-05-17-logging-platform-contract-design.md`](../superpowers/specs/2026-05-17-logging-platform-contract-design.md). | Single agent owns the log path. Apps emit the envelope and nothing else; the agent supplies identity from container labels; severity is bounded at ingest so Loki labels stay bounded. Backend swap (Datadog / Splunk / managed Loki) means changing the sink, nothing else. | Managed Loki backend; per-source remaps for the no-op-default sources when SREs want severity filtering on them; PII redaction processor wired upstream of the sink; per-environment sampling tiers. |
| Structured-log contract | App containers (server, www) emit one JSON object per stdout line: `timestamp` (RFC 3339 UTC ms), `level` (lowercase enum: `trace`/`debug`/`info`/`warn`/`error`/`fatal`), `message`, `trace_id` + `span_id` (lowercase hex W3C, when an OTel span is active), plus free-form extras. Resource attributes (`service.name`, `module_name`, `owned_by`, `deployment.environment.name`) are **not** in the envelope — the Vector agent supplies them from container labels (next row). Rust: `tracing-subscriber::fmt::layer().json()` + `tracing-opentelemetry` bridge; root span is just `tracing::info_span!("app")`. The `ErrorLogLayer` Tower middleware logs non-OK gRPC `Status` returns at WARN/ERROR with `trace_id` and `span_id` pulled from the active OTel span (the JSON formatter doesn't auto-bridge those into event records). www: Pino with no `base:` block; `formatters.log` injects active OTel context. Per-language emitter recipes for other stacks (Go / Python / JVM / Ruby / .NET) live in the rules doc. | Apps stay dumb. Same JSON shape across languages. Conforming costs one package + 5 lines of init. | Per-language recipe verification for the four unverified rows when a service in any of those languages joins the catalogue. |
| Bonuses | All six items from `requirements.md` in scope. | OTel (OpenTelemetry)-everywhere carries logging and error handling; catalogue argument carries data design. | Per-bonus mapping in the spec. |
| Trusted localdev TLS | LocalMesh CA installed into the host trust store via `mkcert -install`, wrapped by `localmesh ca install` (mkcert v1.4.4 vendored at `localmesh_src/tools/mkcert`, linux-amd64). CA material lives at `.localmesh/secrets/root_ca/`. `${LOCAL_DOMAIN}` defaults to `lvh.me` (magic DNS — every subdomain resolves to 127.0.0.1) so no `/etc/hosts` editing is needed; `local_domain` in `project.toml` overrides if a real local DNS is preferred. | The whole "is this cert trusted?" debate gets resolved at `make setup` time. `mkcert` is purpose-built for cross-platform trust-store registration (NSS / system store / Firefox); vendoring the binary removes the host-install prerequisite. lvh.me removes the last "sudo on first run" step. | Real internal DNS + cert-manager-issued IngressRoute certs at the cluster ingress. Per-host certs (no wildcards) in prod. |

### Process notes (not architecture)

- **Tests:** Rust unit/integration in `server/`; Next.js tests in `www/`. High-value tests only — PoC (Proof of Concept) scope.
- **Commit hygiene:** test changes and code changes never share a commit; code commits require a green tree.

## Open

V0 questions still in flux. Production-scope questions live in [`PRODUCTION_DISCUSSIONS.md`](./PRODUCTION_DISCUSSIONS.md).

- **mTLS demonstration depth.** Minimum: server logs successful connection at startup. Reviewer-visible: on-demand gRPC method + UI button.
- **Collector → TSDB mTLS on the dev path.** Plain HTTP for now; uniform with the Rust→TSDB hop is possible at small cost.
- **Outbound client metrics.** Apps now emit OTel-semconv server metrics (`rpc.server.duration` from the Rust tower middleware; `http.server.request.duration` from `@opentelemetry/instrumentation-http` in www) — those land the RED rows on the imported APM dashboard. Outbound client metrics (`http.client.duration`, `db.client.duration`, `rpc.client.duration`) are still partial: Node's auto-instrumentation emits HTTP-client metrics by default; the Rust client paths (reqwest → Grafana, sqlx → postgres, tonic-client from www-as-grpc-client) need explicit instrumentation. Outbound panels on the dashboard stay sparse until that lands.
- **Panel types beyond Timeseries.** Stat and Table variants stubbed in `metrics.proto` — handler returns `UNIMPLEMENTED`. Wired when a reviewer use-case appears; panel JSON differs only in `type` + a couple of option fields per type, so it's mostly mechanical.
- **Identity source consolidation.** `plugin.toml` (and `project.toml` for app-tier services) is now the source of truth for the per-plugin halves of the identity tuple, with the binding convention canonical in [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md) §1. `localmesh build` (`internal/envwriter`) reads them and emits per-plugin UPCASE_SNAKECASE entries into `.env`'s managed section; compose interpolates them onto docker labels + `OTEL_RESOURCE_ATTRIBUTES`. Working bridge; the proper replacement (build-step compose overlay generator, or a real compose extension once compose grows one) is `TODO: needs_prod_decisions plugin.toml → compose interpolation` in `TODO.md`.
- **Convention linter.** Plugin conventions (identity tuple + `README.md` per plugin, per [`plugin-conventions.md`](../engineering/rules/plugin-conventions.md)) ship as documentation now. A v0+1 linter should check: every catalog plugin's services carry the full identity tuple matching the directory slug; every app-tier service carries `module_name=app`; every plugin directory with a `docker-compose.yml` and a consumer surface has a `README.md`; each `README.md` has the eight section headings in order. See [`2026-05-18-localmesh-namespacing-and-plugin-exports-design.md`](../superpowers/specs/2026-05-18-localmesh-namespacing-and-plugin-exports-design.md) §3.4 + §4.6.
- **Default-dashboard reconciliation.** Picker cleanup across the default dashboards (`database/postgres.json`, `observability/apm.json`, `observability/cluster-health.json`) — drop the `environment` picker, standardise identity-axis pickers on `namespace` + `service`/`container_name`. Deferred from the conventions implementation because parallel dashboard work would intersect; intent + constraints captured in `docs/TODO.md`'s Dashboards section.

## Deviations from `requirements.md`

- **Agent → Server arrow is layered.** Off-the-shelf collector receives; TSDB stores; Rust server is the application API in front. *"The server"* in the requirements' sense is the layered tier.
- **Server in Rust** — satisfies the literal requirement.
- **Agent in Python** (Tasks section) — superseded by Core Requirements' "any language." Off-the-shelf collector instead, packaged as a catalogue module.
